# 第一部分：全局约定

## 1.1 服务与路径

| 项 | 值 |
|---|---|
| 后端端口 | `8080` |
| 管理端 nginx 端口 | `9000` |
| 管理端访问前缀 | `/api/**` → nginx 转发到后端 `/admin/**` |
| 用户端访问前缀 | `/user/**` → nginx 转发到后端 `/user/**` |
| WebSocket | `/ws/**` |
| 静态资源（上传文件） | 阿里云 OSS 公网 URL |

客户端**不直接访问 8080**，一律经 nginx `9000` 转发。

## 1.2 统一返回格式

所有接口（含 WebSocket 之外的全部 HTTP 接口）返回统一结构：

| 字段 | 类型 | 含义 |
|---|---|---|
| `code` | Integer | **1 = 成功**；0 或其它 = 失败 |
| `msg` | String | 错误提示文本，成功时为 `null`（部分接口为空串） |
| `data` | T | 业务数据，无数据时为 `null` |

分页接口的 `data` 固定为 `PageResult`：

| 字段 | 类型 | 含义 |
|---|---|---|
| `total` | Long | 总记录数 |
| `records` | Array | 当前页数据列表 |

**前端判定约定（统一）**：`code === 1` 为成功。原管理端判 `code === 1`、原小程序判 `code == 200 || code === 1`，新项目统一收敛为 `code === 1`。

失败示例：

```json
{ "code": 0, "msg": "账号不存在", "data": null }
```

## 1.3 鉴权

| 端 | token 位置 | 请求头字段 | 有效期 |
|---|---|---|---|
| 管理端 | 浏览器 Cookie（key = `token`） | `token` | 7200000 ms |
| 用户端 | 客户端状态（Pinia / vuex） | `authentication` | 7200000 ms |

- 签发方式：JWT，密钥分别由 `xianhe.jwt.admin-secret-key` / `xianhe.jwt.user-secret-key` 配置。
- 请求头缺失或 token 非法：返回 `code = 0`，`msg = "登录状态已失效"`，前端跳登录页。
- 放行白名单：`POST /admin/staff/login`、`POST /user/member/login`、`GET /user/shop/status`。
- 当前登录人标识存于服务端 `BaseContext`（ThreadLocal），业务层不接收前端传入的操作人 id。
- **WebSocket 握手**：浏览器建连不能带自定义请求头，管理端令牌须放在查询参数里 —— `ws://<host>/ws/{sid}?token=<管理端令牌>`。
  服务端在 `onOpen` 用与管理端接口同一把密钥验签，失败以 `1008` 关闭连接；`sid` 由前端生成并持久化，同一 `sid` 重连会顶掉旧连接。

## 1.4 错误约定

- **不使用数字错误码体系**，与后端 `MessageConstant` 保持一致：异常全部由 `GlobalExceptionHandler` 捕获并转为 `Result.error(msg)`。
- `msg` 取值来源：`BaseException` 各子类的异常消息、`MessageConstant` 常量文本、唯一索引冲突时解析出的「xxx 已存在」。
- 常见 `msg` 清单：

| msg | 触发场景 |
|---|---|
| 账号不存在 / 密码错误 / 账号被锁定 | 登录失败 |
| 登录状态已失效 | token 缺失或非法 |
| 分类下关联商品，无法删除 | 删除分类校验 |
| 商品不存在 / 组合箱不存在 | 详情查询、明细引用了已删除的记录 |
| 商品处于上架状态，不能删除 | 删除商品校验：含上架中的商品 |
| 商品关联组合箱，不能删除 | 删除商品校验：含被组合箱引用的商品 |
| 所属分类已禁用，无法上架 | 商品上架校验：所属分类 status = 0 |
| 商品被起售中的组合箱引用，无法下架 | 商品下架校验 |
| 组合箱处于起售状态，不能删除 | 删除组合箱校验 |
| 微信登录失败 | 用户端登录：code 换不到 openid |
| 购物车为空 | 用户端减购：该记录已不在购物车 |
| 商品或组合箱必须二选一 | 用户端加购 / 减购：请求体没带 goodsId 也没带 bundleId |
| 组合箱内含商品未上架，无法起售 | 组合箱起售校验：内含商品存在下架项 |
| 所属分类已禁用，无法起售 | 组合箱起售校验：所属分类 status = 0 |
| 组合箱至少需要一个内含商品 | 新增 / 修改组合箱校验 |
| 组合箱内含商品重复 | 新增 / 修改组合箱校验 |
| 内含商品的份数必须大于 0 | 新增 / 修改组合箱校验 |
| 分类不存在 / 分类类型不匹配 | 商品、组合箱引用分类校验 |
| 商品规格的名称与候选值不能为空 | 新增 / 修改商品校验 |
| 购物车为空 / 收货地址为空 | 下单前置校验 |
| 订单状态错误 / 订单不存在 | 订单流转校验 |
| 启用中的店员不能删除 | 删除店员校验：目标账号 status = 1 |
| 不能删除当前登录账号 | 删除店员校验：目标 id 等于当前登录人 |

## 1.5 业务字典

**订单状态 `order_main.status`**

| 值 | 含义 | 可流转到 |
|---|---|---|
| 1 | 待付款 | 2、6 |
| 2 | 待接单 | 3、6 |
| 3 | 已接单 | 4、6 |
| 4 | 派送中 | 5 |
| 5 | 已完成 | — |
| 6 | 已取消 | — |
| 7 | 退款 | — |

> ⚠️ `status = 7` 是**字典预留值**（与原项目一致）：本项目没有写入该状态的接口。已支付订单被拒单或取消时置为 `6` 已取消，同时把 `pay_status` 置为 `2` 已退款——**「钱退没退」由 `pay_status` 承担，不由 `status` 承担**，避免两个字段表达同一件事。

> **下单与支付是两个独立动作，不绑定。**
>
> | 动作 | 接口 | 结果 | 谁可见 |
> |---|---|---|---|
> | ① 提交订单 | `POST /user/order` | `status = 1` 待付款、`pay_status = 0`、`checkout_time` 为空 | 管理端「待付款」页签立即可见 |
> | ② 支付订单 | `PUT /user/order/payment` | `status = 1 → 2` 待接单、`pay_status = 0 → 1`、写入 `checkout_time` | 管理端「待付款」角标 -1，「待接单」+1，并收到来单提醒 |
>
> 因此 **`status = 1` 是一等状态**：它可被查询、可被统计、可被用户主动取消，也会被超时任务自动取消（见 2.8.9）。`status = 2` 与 `pay_status = 1` 严格同源——进入 2 的唯一入口就是支付成功。
>
> 订单状态推进责任划分：`1 → 2` 由**用户支付**触发；`2 → 3` 由**店员接单**触发；`3 → 4` 由**店员派送**触发；`4 → 5` 由**店员完成**触发；`→ 6` 可由用户取消、店员拒单/取消、或系统超时任务触发；`pay_status = 2` 仅在**已支付订单**被取消/拒单时写入。

**支付状态 `order_main.pay_status`**

| 值 | 含义 |
|---|---|
| 0 | 未支付 |
| 1 | 已支付 |
| 2 | 已退款 |

**启停状态 `status`**（`staff` / `goods` / `bundle` / `goods_category` 共用）

| 值 | 含义 | 各业务对象的说法 |
|---|---|---|
| 0 | 未启用 | 店员「已禁用」/ 分类「已禁用」/ 商品「已下架」/ 组合箱「已停售」 |
| 1 | 已启用 | 店员「已启用」/ 分类「已启用」/ 商品「已上架」/ 组合箱「已起售」 |

> **统一规则一：新增一律为 0。** 所有带状态的数据新增后都是未启用状态，由使用者确认无误后手动启用；
> 状态变更一律走各模块的 `status/{status}` 接口 —— **新增与修改接口都不接收 `status`**，
> 否则那条路径上的启用校验会被绕开。

> **统一规则二：在售即完好。** 涉及「在售」的三方联动，缺一条就会出现自相矛盾的状态：
> - **商品上架** ⇒ 所属分类必须处于启用状态（上架接口与修改接口都校验）；
> - **组合箱起售** ⇒ 内含商品全部上架、且所属分类处于启用状态（起售接口与修改接口都校验）；
> - **商品下架** ⇒ 不能被起售中的组合箱引用（停售中的组合箱不算）。

**温区 `storage_zone`**

| 值 | 含义 |
|---|---|
| 1 | 常温 |
| 2 | 冷藏 |
| 3 | 冷冻 |

**分类类型 `goods_category.type`**

| 值 | 含义 |
|---|---|
| 1 | 商品分类 |
| 2 | 组合分类 |

**配送时效 `order_main.delivery_status`**

| 值 | 含义 |
|---|---|
| 1 | 尽快送达（默认） |
| 0 | 预约时段 |

**支付方式 `order_main.pay_method`**

| 值 | 含义 |
|---|---|
| 1 | 微信支付（唯一选项，降级实现） |
| 2 | 支付宝（预留，不实现） |

## 1.6 公共字段约定

以下字段由 AOP 自动填充（`@AutoFill`），**前端不传**：

# 第二部分：管理端接口

## 2.1 店员模块 `/admin/staff`

### 2.1.1 店员登录

- **方法与路径**：`POST /admin/staff/login`
- **鉴权**：白名单，不需要 token
- **请求参数**

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `username` | String | 是 | 用户名 |
| `password` | String | 是 | 密码（HTTPS 传输；服务端用 PBKDF2 + 随机盐校验，兼容存量 MD5 并在登录后自动升级） |

- **响应 data**（`StaffLoginVO`）

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | Long | 店员 id |
| `userName` | String | 用户名 |
| `name` | String | 姓名 |
| `token` | String | JWT 令牌，前端写入 Cookie key `token` |

- **示例**

```json
// 请求
{ "username": "manager", "password": "123456" }
// 响应
{ "code": 1, "msg": null, "data": { "id": 1, "userName": "manager", "name": "周岚", "token": "eyJhbGciOiJIUzI1NiJ9..." } }
```

### 2.1.2 店员退出

- **方法与路径**：`POST /admin/staff/logout`
- **鉴权**：需要 token
- **请求参数**：无
- **响应 data**：`null`
- **示例**：`{ "code": 1, "msg": null, "data": null }`

### 2.1.3 新增店员

- **方法与路径**：`POST /admin/staff`
- **鉴权**：需要 token
- **请求参数**（`StaffDTO`）

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `name` | String | 是 | 姓名，≤32 字符 |
| `username` | String | 是 | 用户名，≤32 字符，全局唯一 |
| `phone` | String | 是 | 手机号，11 位 |
| `sex` | String | 是 | 性别，`男` / `女` |
| `idNumber` | String | 是 | 身份证号，18 位 |

- **响应 data**：`null`
- **说明**：
  - 初始密码由服务端固定为 `123456`（PBKDF2 + 随机盐存储）。
  - **状态由服务端固定为「禁用」（`status = 0`），不接受前端传入**；需在店员列表中手动启用后该账号才能登录。
    这是全局约定：**所有带状态的数据新增后一律为禁用 / 下架 / 停售**，由使用者确认无误后再启用。

### 2.1.4 店员分页查询

- **方法与路径**：`GET /admin/staff/page`
- **鉴权**：需要 token
- **请求参数**

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `name` | String | 否 | 姓名，模糊匹配 |
| `username` | String | 否 | 用户名，模糊匹配 |
| `phone` | String | 否 | 手机号，模糊匹配 |
| `page` | Integer | 是 | 页码，从 1 开始 |
| `pageSize` | Integer | 是 | 每页条数 |

- **响应 data**：`PageResult`，`records` 元素为 `Staff` 实体

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | Long | 主键 |
| `name` | String | 姓名 |
| `username` | String | 用户名 |
| `phone` | String | 手机号 |
| `sex` | String | 性别 |
| `idNumber` | String | 身份证号 |
| `status` | Integer | 启停状态 |
| `createTime` | String | 创建时间 |
| `updateTime` | String | 更新时间 |

- **说明**：按 `create_time` 倒序；**不返回 `password`**。三个筛选条件之间是 AND 关系，均为空时返回全部。

### 2.1.5 启用/禁用店员账号

- **方法与路径**：`POST /admin/staff/status/{status}`
- **鉴权**：需要 token
- **路径参数**：`status` — 0 禁用 / 1 启用
- **请求参数**：`id`（Long，必填，表单或 query 传递）
- **响应 data**：`null`

### 2.1.6 根据 id 查询店员

- **方法与路径**：`GET /admin/staff/{id}`
- **鉴权**：需要 token
- **路径参数**：`id` — 店员 id
- **响应 data**：`Staff` 实体（不返回 `password`）
- **说明**：管理端「个人主页」也复用本接口获取当前登录人信息（id 取自登录响应）。

### 2.1.7 编辑店员

- **方法与路径**：`PUT /admin/staff`
- **鉴权**：需要 token
- **请求参数**（`StaffDTO`，含 `id`）

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `id` | Long | 是 | 店员 id |
| `name` | String | 是 | 姓名 |
| `username` | String | 是 | 用户名 |
| `phone` | String | 是 | 手机号 |
| `sex` | String | 是 | 性别 |
| `idNumber` | String | 是 | 身份证号 |

- **响应 data**：`null`

### 2.1.8 修改密码（新增接口）

- **方法与路径**：`PUT /admin/staff/editPassword`
- **鉴权**：需要 token
- **请求参数**（`PasswordEditDTO`）

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `empId` | Long | 是 | 店员 id（前端从登录响应取，个人主页提交） |
| `oldPassword` | String | 是 | 原密码（明文） |
| `newPassword` | String | 是 | 新密码（明文） |

- **响应 data**：`null`
- **失败场景**：`msg = "原密码错误"`（`PASSWORD_EDIT_FAILED`）
- **示例**

```json
{ "empId": 1, "oldPassword": "123456", "newPassword": "xh@2026" }
```

### 2.1.9 删除店员

- **方法与路径**：`DELETE /admin/staff`
- **鉴权**：需要 token
- **请求参数**：`id`（Long，必填，query 传递）
- **响应 data**：`null`
- **说明**：**物理删除**（直接 `DELETE FROM staff`），不做逻辑删除。删除前做两项校验，任一不通过即拒绝：
  1. 目标账号处于启用状态时不允许删除——要求先禁用，避免误删仍在使用的账号（与「起售中不能删除」「关联数据不能删除」是同一套思路）；
  2. 不允许删除当前登录的账号——否则操作人会当场失去登录能力。
- **失败场景**

| `msg` | 触发场景 |
|---|---|
| 启用中的店员不能删除 | 目标账号 `status = 1` |
| 不能删除当前登录账号 | 目标 id 等于当前登录人 id |

## 2.2 商品分类模块 `/admin/goodsCategory`

### 2.2.1 新增分类

- **方法与路径**：`POST /admin/goodsCategory`
- **鉴权**：需要 token
- **请求参数**（`GoodsCategoryDTO`）

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `type` | Integer | 是 | 分类类型：1 商品分类 / 2 组合分类 |
| `name` | String | 是 | 分类名称，≤32 字符，全局唯一 |
| `sort` | Integer | 是 | 排序值，越小越靠前；**必填**（库中 `sort` 为 `NOT NULL`） |

- **响应 data**：`null`
- **说明**：**新增后状态为「禁用」（`status = 0`）**，需在分类列表中手动启用后用户端才可见。
  与店员新增同一约定：带状态的数据一律先禁用，确认无误后再启用。`sort` 为必填，前端表单需校验非空。

### 2.2.2 分类分页查询

- **方法与路径**：`GET /admin/goodsCategory/page`
- **鉴权**：需要 token
- **请求参数**

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `name` | String | 否 | 分类名称，模糊匹配 |
| `type` | Integer | 否 | 分类类型筛选 |
| `page` | Integer | 是 | 页码 |
| `pageSize` | Integer | 是 | 每页条数 |

- **响应 data**：`PageResult`，`records` 为 `GoodsCategory` 实体：`id`、`type`、`name`、`sort`、`status`、`createTime`、`updateTime`
- **说明**：**`status` 不作为查询条件**——管理端必须能查到禁用中的分类，否则一旦禁用就再也查不到、无法恢复。

### 2.2.3 删除分类

- **方法与路径**：`DELETE /admin/goodsCategory`
- **鉴权**：需要 token
- **请求参数**：`id`（Long，必填，query 传递）
- **响应 data**：`null`
- **失败场景**：分类下关联商品或组合箱 → `msg = "分类下关联商品，无法删除"`

### 2.2.4 修改分类

- **方法与路径**：`PUT /admin/goodsCategory`
- **鉴权**：需要 token
- **请求参数**：`id`（必填）、`name`（必填）、`sort`（必填）

## 2.6 商品模块 `/admin/goods`

### 2.6.1 新增商品

- **方法与路径**：`POST /admin/goods`
- **鉴权**：需要 token
- **请求参数**（`GoodsDTO`）

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `name` | String | 是 | 商品名称，≤32 字符，全局唯一 |
| `categoryId` | Long | 是 | 所属商品分类 id（`type = 1`） |
| `price` | BigDecimal | 是 | 售价 |
| `image` | String | 否 | 图片 URL，可为空 |
| `description` | String | 否 | 描述，≤255 字符 |
| `origin` | String | 否 | 产地，≤64 字符 |
| `shelfLife` | String | 否 | 保质期文案，如「5 天」 |
| `storageZone` | Integer | 是 | 温区：1 常温 / 2 冷藏 / 3 冷冻 |
| `specs` | Array | 否 | 规格列表，见下 |

`specs` 元素结构：

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `name` | String | 是 | 规格类型，如「净重」「加工方式」 |
| `value` | String[] | 是 | 候选值数组，如 `["约500g","约1kg"]` |

- **响应 data**：`null`
- **说明**：
  - `specs[].value` 在接口层是数组，服务端序列化为 JSON 文本后存入 `goods_spec.value`。
  - **新增后商品状态固定为「下架」（`status = 0`）**，需在商品列表中手动上架。
    这是全局约定：所有带状态的数据新增后一律为禁用 / 下架 / 停售。
  - `categoryId` 必须是 `type = 1` 的商品分类：分类不存在返回「分类不存在」，传组合分类返回「分类类型不匹配」。
  - `specs` 的每一组都必须有名称且至少一个候选值；空白候选值由服务端丢弃，
    出现空名称或丢完为空的分组返回「商品规格的名称与候选值不能为空」。
  - 商品名称重复由唯一索引兜住，返回「xxx已存在」。
- **示例**

```json
{
  "name": "本地小番茄",
  "categoryId": 2,
  "price": 9.90,
  "image": null,
  "description": "产地直采，当日采摘当日达",
  "status": 1,
  "origin": "山东寿光",
  "shelfLife": "冷藏 5 天",
  "storageZone": 2,
  "specs": [
    { "name": "净重", "value": ["约500g", "约1kg"] },
    { "name": "包装", "value": ["散装", "礼盒装"] }
  ]
}
```

| `name` | String | 商品名称 |

### 2.6.3 批量删除商品

- **方法与路径**：`DELETE /admin/goods`
- **鉴权**：需要 token
- **请求参数**：`ids`（String，必填，逗号分隔，如 `1,2,3`）
- **响应 data**：`null`
- **失败场景**：
  - 含上架中商品 → `msg = "商品处于上架状态，不能删除"`
  - 含被任何组合箱（不论组合箱是否在售）引用的商品 → `msg = "商品关联组合箱，不能删除"`
- **说明**：
  - 两道校验的先后顺序固定为「先看上架、再看引用」，报出的 `msg` 与之一致。
  - 通过校验后在一个事务内依次删除 `goods`、`goods_spec`，以及 `cart` 中引用这些商品的行 ——
    购物车行在目标商品消失后已无意义，留着只会在结算时报「商品不存在」。
  - `ids` 为空时不报错、也不执行任何 SQL。
  - 校验与删除之间不加跨表锁：并发下极端情况（校验通过后又有人上架）不在本项目的数据规模考虑内。

### 2.6.4 根据 id 查询商品

- **方法与路径**：`GET /admin/goods/{id}`
- **鉴权**：需要 token
- **路径参数**：`id` — 商品 id
- **响应 data**（`GoodsVO`）：在 2.6.2 字段基础上增加

| 字段 | 类型 | 含义 |
|---|---|---|
| `specs` | Array | 规格列表，元素为 `{ id, name, value: String[] }` |

- **失败场景**：`msg = "商品不存在"`

### 2.6.5 修改商品

- **方法与路径**：`PUT /admin/goods`
- **鉴权**：需要 token
- **请求参数**：`GoodsDTO` 全部字段 + `id`（Long，必填）。**不含 `status`**
- **响应 data**：`null`
- **说明**：
  - 规格采用**全量覆盖**策略——规格列表以本次提交为准，服务端先按 `goods_id` 删除旧记录再插入新记录。
  - 其余字段**动态更新**：只写提交过来的字段，未提交的保持原值（与店员、分类一致）。
  - 可空字段（`image`、`description`、`origin`、`shelfLife`）**提交空串即清空**——
    前端清空输入框、或点「移除图片」提交的都是空串。清空后的图片按「无图」处理，
    列表与用户端显示「首字 + 温区配色」占位图。
  - 上架中的商品改完名称 / 售价 / 分类后，会**清除该分类的用户端缓存**（否则用户端最长 30 分钟看不到新价）；
    分类若被改过，新旧两个分类的缓存都清。
  - 若该商品当前**处于上架中**，新分类必须处于启用状态，否则返回「所属分类已禁用，无法上架」——
    上架中的商品不允许出现在一个已禁用的分类下。

### 2.6.6 按分类查询商品列表

- **方法与路径**：`GET /admin/goods/list`
- **鉴权**：需要 token
- **请求参数**：`categoryId`（Long，选填）
- **响应 data**：`Goods` 实体数组（不含 `specs`）
- **说明**：管理端「新增组合箱」弹层选择商品时使用。
  - **不过滤 `status`**：已下架商品也要返回并标注出来，否则编辑一个含下架商品的组合箱时，
    弹层里看不到它、一保存就被移除。前端据此把下架商品置为不可选。
  - `categoryId` 不传时返回全部商品。

### 2.6.7 商品上架/下架

- **方法与路径**：`POST /admin/goods/status/{status}`
- **鉴权**：需要 token
- **路径参数**：`status` — 0 下架 / 1 上架
- **请求参数**：`id`（Long，必填）
- **响应 data**：`null`
- **失败场景**：
  - 上架时所属分类处于禁用状态 → `msg = "所属分类已禁用，无法上架"`
  - 下架时该商品被起售中的组合箱引用 → `msg = "商品被起售中的组合箱引用，无法下架"`
    （停售中的组合箱不算：它本身不可售，里面放着下架商品不构成问题）
  - 商品不存在 → `msg = "商品不存在"`
- **说明**：
  - **上架中 ⇒ 所属分类启用**是一条硬规则，上架接口与修改接口都按它校验。
  - 状态变更后**精准清除**该商品所属分类下的用户端缓存 `xh:goods:category:{分类id}`，不清全量。
    该缓存的写入方是用户端商品查询接口（用户端模块实现时接入），键名前缀统一取自 `RedisKeyConstant`，
    避免两端各写一份字符串而写错。

`bundleGoods` 元素结构：

| 字段 | 类型 | 必填 | 含义 |

  - `categoryId` 必须是 `type = 2` 的组合分类，否则返回「分类不存在」/「分类类型不匹配」。
  - 组合箱名称重复由唯一索引兜住，返回「xxx已存在」。

### 2.7.5 修改组合箱

- **方法与路径**：`PUT /admin/bundle`

  - 起售时内含商品存在未上架项 → `msg = "组合箱内含商品未上架，无法起售"`
  - 起售时所属分类处于禁用状态 → `msg = "所属分类已禁用，无法起售"`
  - 组合箱不存在 → `msg = "组合箱不存在"`
- **说明**：
  - **起售中 ⇒ 内含商品全部上架且所属分类启用**。与之配套，商品下架接口会拒绝
    「仍被起售中组合箱引用」的商品，两个方向合起来保证在售组合箱不会缺件。

### 2.8.6 取消订单

- **方法与路径**：`PUT /admin/order/cancel`
- **鉴权**：需要 token
- **请求参数**（`OrderCancelDTO`）

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `id` | Long | 是 | 订单 id |
| `cancelReason` | String | 是 | 取消原因 |

- **响应 data**：`null`
- **业务规则**：**订单未完成（`status ≠ 5`）且未取消（`status ≠ 6`）时可取消**，即 `1` / `2` / `3` / `4` 均可；已支付订单同时置 `pay_status = 2`。
  界面上「取消」按钮只对 `1` 与 `3` 暴露（`2` 走拒单、`4` 走完成），后端不因此把口收紧。
- **失败场景**：`msg = "订单不存在"`、`msg = "订单状态错误"`

### 2.8.9 超时未支付自动取消（后台定时任务，无接口）

- **实现**：Spring Task，`@Scheduled(cron = "0 * * * * ?")`，每分钟执行一次。
- **扫描条件**：`status = 1`（待付款）且 `order_time` 早于「当前时间 - 15 分钟」。
- **处理动作**：`status = 6` 已取消、`cancel_reason = "订单超时未支付，系统自动取消"`、`cancel_time = 当前时间`。
- **说明**：这是「下单与支付分离」的必要配套——没有它，未支付订单会永久停留在待付款页签。因为本项目**不设库存**，取消时不涉及库存回滚；若该订单已支付则不在扫描范围内（`status = 1` 必然 `pay_status = 0`）。
- **无接口**：店员与会员均不可调用，只由任务触发；管理端通过在「已取消」页签看到这些订单及其取消原因。

## 2.9 报表模块 `/admin/report`

> 本模块**不提供 Excel 导出**（原项目的 `/export` 已删除）。全部接口返回 JSON，时间区间参数格式为 `yyyy-MM-dd`。
>
> **时间区间缺省规则**（四个接口一致）：
>
> | 传参情况 | 实际区间 |
> |---|---|
> | `begin` / `end` 都不传 | 最近 **30 天**（含今天），即 `今天-29` ~ `今天` |
> | 只传 `end` | `end-29` ~ `end` |
> | 只传 `begin` | `begin` ~ `今天` |
> | `begin` 晚于 `end` | 返回空序列（`dateList` 为空串），不报错 |
>
> 日期格式非法（如 `begin=not-a-date`）会走全局兜底，返回 `code = 0`、`msg = "未知错误"`——这是参数绑定失败的统一表现，管理端的日期选择器不会产出这种值。
